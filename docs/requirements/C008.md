## 1. 用户确认与范围

用户满意 v0.6.0-test2。新增目标是直接在沙二 3D 地图中观察随时间变化的烟雾体积和火焰效果，具体例子包括小道瀑布烟、中路挂门烟及爆点火，并希望能组合查看多颗道具。

用户接受以实际游戏视频或图片为参考制作接近的效果；最新决定是“先做最厉害的，假如说不行，再退而求其次”。因此先验证受地形约束的动态三维模拟，视频参考作为标定证据和后备方案，不能一开始就把固定圆球或平面视频作为最终效果。

“高目标”按具体行为验收：烟雾随时间扩散、受墙壁和门洞约束、进入连通的上下层空间；火沿允许的地面区域蔓延；用户换视角观察时，空间关系和遮挡保持一致。接近 CS2 的目标不等于已经拥有原版算法，也不预先承诺尺寸、时序、投法或边界完全一致。

人物落地步行、台阶和坡道是用户明确说明的非刚需，本轮仍处于评估，不能作为烟火验证的前置阻塞；继续保留现有自由视角。

## 3. 验证顺序与调整规则

1. 先完成空间查询和最小动态烟雾验证：实体墙阻隔、门洞连通、上下层扩散、进入烟内观察和消散。
2. 在明确地图位置后，以一个瀑布烟作为首个沙二案例，记录落点、空间范围和时间序列；中路挂门烟用于验证门洞约束。
3. 单独实现并验证火的地面覆盖、蔓延和消退，再验证多颗道具组合。烟的三维扩散与火的地面传播不能混用同一规则。
4. 先优化局部计算范围、空间索引、分辨率、透明绘制和更新预算；保留清楚的效果差异和实测记录，再判断高目标能否用于手机。
5. 如遇不可接受的性能、资料或精度限制，由项目经理先说明问题和拟调整范围，再切换到视频标定的点位三维效果预设。用户已允许必要时退而求其次；这不表示所有低档方案已验证可用。

采用体素/密度场、粒子或其他方案是实现选择，不是对 CS2 内部算法的断言。优先做小范围证据，避免先改整套地图和渲染架构后才检查能否运行。

## 5. 接口需要约定的内容

在编码之前明确以下信息并提交小样；本文件不擅自冻结未验证的二进制格式。

- 几何查询：坐标空间、单位、有效层、实体变换、射线/邻接/遮挡行为与数值容差。raw 为 Source XYZ / Z-up，显示为 [x*0.0254,z*0.0254,-y*0.0254]；转换只做一次，不把显示比例当成已认证游戏物理参数。
- 道具事件：类型、落点/起效位置、起效时间、随机种子或重播状态、参数版本；区分人工指定起效点与已验证投掷落点。
- 动态状态：烟的空间密度与时间、火的地面覆盖与时间、最大活动数量、局部内存范围、质量参数。
- 渲染状态：与场景深度和透明材质的关系、镜头进入烟内的表现、GL 上下文恢复及资源释放。
- CPU/GPU 工作划分：后台计算有界，GL 操作仍在 GL 线程，不抢占 C007 资源加载造成明显回退；不把增加线程数当作已经提速的证据。

先验证烟火起效后的体积与覆盖。若投掷轨迹尚未校准，不能将“人工放置起效点”标为“任意投法已准确模拟”；两项进度单独记录。
